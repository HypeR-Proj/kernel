# x86-64 architecture profile

x86-64 is an experimental HypeR architecture. AArch64 remains tier 1 and
defines the semantic baseline for architecture-neutral kernel interfaces. The
x86-64 port exists as a QEMU-targeted implementation and as a continuing audit
of the `arch`/HAL/platform boundaries; x86 mechanisms must not leak into the
common interfaces merely to resemble Arm concepts.

## Host contract

The initial hardware host profile requires long mode, NX, x2APIC, an invariant TSC, and
four logical CPUs. VM execution selects Intel VMX/EPT or AMD SVM/NPT at runtime.
The Intel backend requires four-level write-back EPT and single-context INVEPT;
the AMD backend requires nested paging, a usable guest ASID, and Next-RIP Save.
TSC-deadline mode
is preferred. The x2APIC backend calibrates and uses its one-shot timer when a
host or emulator does not advertise TSC-deadline; this keeps host scheduling
and IRQ-stack tests meaningful under QEMU TCG without weakening the VMX
requirement for guest execution. QEMU TCG is the sole invariant-TSC advertising
exception: HypeR recognizes its `TCGTCGTCGTCG` hypervisor vendor and uses the
emulator's synchronized virtual TSC only for the host smoke test.

The supported virtual board is QEMU `q35`. QEMU's Linux direct-kernel loader
passes a Linux-format boot-parameter block, command line, initramfs, and a DTB
`setup_data` record. The five-sector HypeR setup image normalizes this handoff,
enters long mode, applies image relocations, and transfers to the Rust
bootstrap. The final host address space separates the high kernel mapping,
RAM linear map, MMIO window, and guarded stack arena.

The root interrupt controller is x2APIC. HypeR masks both legacy 8259 PICs
before enabling local APIC delivery, uses per-CPU TSS interrupt-stack-table
entries for IRQ and emergency stacks, and starts secondary processors through
an INIT/SIPI trampoline below 1 MiB. Port I/O is an explicit HAL capability;
the NS16550 driver uses it for the optional
`earlycon=uart8250,io,0x3f8` console.

Runtime vector entry preserves the interrupted x87/SSE and MXCSR state with a
16-byte-aligned FXSAVE area before calling Rust. The x86-64 build explicitly
disables AVX-family code generation; enabling wider vector state requires a
CPUID/XCR0-derived XSAVE contract first.

## Guest contract

There is no current end-to-end x86-64 Linux guest launch path. The former
in-kernel bzImage loader was removed; Native application execution and a
userspace x86-64 VM loader are still required. The mechanisms below remain
implemented, but do not by themselves provide a bootable guest configuration.

EPT or NPT owns guest-physical memory and uses the architecture-independent
sparse guest-memory allocator. Second-level translation faults feed the same
demand-paging policy as the Arm and RISC-V stage-2 fault paths, followed by the
backend's context-scoped invalidation. VM-exit entry preserves integer and
FXSAVE state before calling Rust. VMX
entry/exit MSR lists keep syscall and kernel-GS state private to the vCPU and
restore the corresponding host MSRs before any Rust exit handler runs. The
SVM path uses per-CPU VMCB and host-save pages, explicit VMLOAD/VMSAVE state
transfer, and MSR/I/O permission maps. The
VM-service device model provides the legacy PIC/PIT programming surface and a
COM1 console with transmit-empty IRQ4 delivery. Architecture code decodes
VM-exit I/O fields and delegates register semantics to that reusable model; it
does not own board-device state.
The guest contract deliberately omits an xAPIC, x2APIC, AVX, and recognized
paravirtual provider.

## Test boundary

QEMU TCG does not implement VMX/SVM or TSC-deadline. The optional local TCG
smoke test therefore requires four-core host boot, scheduler/synchronization
tests, guarded IRQ/emergency-stack tests, and periodic timer delivery.
It does not invoke a Linux loader.

The public GitHub Actions x86-64 job currently provides compile, Clippy, link,
and image validation only. It does not assume `/dev/kvm`, nested VMX, or SVM.
Guest boot acceptance is deferred until x86-64 Native execution and userspace
VMM support are available. A hardware-assisted host does not restore the
removed in-kernel Linux startup path.

Current limitations include one guest vCPU, no virtual IOAPIC/local APIC,
minimal legacy PIC/PIT semantics, no PCI/virtio devices, and no VM migration or
vCPU preemption path. These are VM-service limitations, not HAL contracts.
